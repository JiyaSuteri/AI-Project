01 • Problem Statement

Why Traditional Restaurant Seating Fails

Manual seating and basic booking apps cannot optimize a busy dining floor in real time.

1. Wasted Table Capacity

  • A 2-person party gets seated at a 6-seat or 8-seat table.
  • Wastes up to 75% of that table's seats during rush hour.
  • Larger families are forced to wait outside.

2. Uneven Waiter Workload

  • One waiter gets 4–5 busy tables while another is free.
  • Causes slow orders, tired staff, and service mistakes.

3. Queue Walk-Outs (Reneging)

  • Long, poorly managed waiting times make guests leave.
  • Simple First-Come-First-Serve ignores VIPs and party sizes.

4. Policy & Hygiene Mistakes

  • Risk of double-booking or seating guests at uncleaned tables.
  • Legacy tools (like OpenTable) only record bookings—they don't run AI optimization.

04 • AI Search Paradigms

Comparing 5 Table Allocation Algorithms

All 5 algorithms run on identical data in backend/app/algorithms/.

Algorithm How It Picks Tables Pros Limitations
Rule-Based Sorted wait time + IF/ELSE zone & smallest fit Ultra-fast, easy to follow Cannot balance competing costs
Greedy Picks lowest cost for each group one-by-one Very fast, logs rejected options Myopic — can trap later groups
BFS Queue (deque) exploring level by level Finds fewest-step allocation High memory; ignores edge cost order
DFS Stack exploring deep branches first Low memory usage Often settles on high-waste tables
A* Search (Best) Min-Heap (heapq) using f(n) = g(n) + h(n) Optimal total cost across all parties Bounded at 6,000 nodes max
05 • Mathematical Formulation

Cost Function & Why A* Is Optimal

Every candidate (Customer, Table, Waiter) match receives a numerical penalty score (lower = better).

Cost = 12.0 × (Empty Seats) + 25.0 × (Waiter Load Ratio) + 0.5 × (WaitMins / 10) / Priority + 20.0 × (Zone Miss)

📊 What the Weights Mean

  • 12.0 × Empty Seats: Stops 2 guests from taking an 8-top table.
  • 25.0 × Waiter Load: Stops one waiter from getting overloaded.
  • Wait & Priority: Higher priority VIPs (1–4) get seated sooner.
  • 20.0 × Zone Miss: Honors Window, Booth, or Patio requests.

✅ Why Heuristic h(n) Is Admissible

  • A* uses f(n) = g(n) + h(n).
  • h(n) only counts minimum possible seat waste + wait cost for remaining groups.
  • It intentionally ignores waiter & zone penalties (≥ 0).
  • So h(n) ≤ true cost h*(n) always — guaranteeing the lowest-cost solution!

Tracks party size, priority, wait time, and leaves (RENEGED) if patience runs out.

07 • Discrete-Event Simulation

Testing Rush Hours With the Simulator

Located in backend/app/simulation/simulator.py and SimulationPage.jsx.

⚙️ Configurable Inputs

  • Number of customer parties (2 to 50)
  • Choice of AI algorithm (A*, Greedy, BFS, DFS, Rule-Based)
  • Arrival interval, dining duration & cleaning time (seconds)
  • Random seed for repeatable experiments

📈 What Happens Each Step

  • Step 1: New parties arrive and join queue (ARRIVAL).
  • Step 2: Impatient guests leave if wait > limit (RENEGED).
  • Step 3: Finished tables move to CLEANING, then AVAILABLE.
  • Step 4: ManagerAgent seats waiting guests (ALLOCATED).
Saved Metrics: Every completed run logs total_customers, successful_allocations, average_waiting_time, execution_time (ms), and utilization (%) into SQLite (simulation_records).
08 • Generative AI & RAG

Grounded AI Concierge (Zero Hallucination)

Combines local policy search (RAG) with live SQLite database facts.

🔍 4-Step Answer Pipeline

  • 1. Policy Indexing: Reads 4 .md policy files using Scikit-Learn TF-IDF.
  • 2. Live DB Snapshot: Queries open tables, queue, and waiter loads from SQLite.
  • 3. Strict Prompting: Tells the LLM: "Never invent fake tables or staff."
  • 4. Groq LPU Inference: Answers fast via openai/gpt-oss-120b (temp = 0.2).

🛡️ Built-In Offline Reliability

  • Primary: Groq API (groq_client.py)
  • Secondary: Anthropic Claude 3.5 Sonnet (claude_client.py)
  • Fallback: Deterministic Python engine (assistant_service.py)
  • Even with zero internet or no API keys, the chat still answers accurately from SQLite!
